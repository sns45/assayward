# Task 1.15 Report: M1 Determinism Gate

## Test Design

### File
`pkg/core/engine/determinism_test.go` (package `engine_test`)

### TestEvaluateDeterminism

Calls `engine.Evaluate` 100 times per built-in policy (baseline, slsa-l3, serverless-edge)
with identical inputs: `goldenEvidence(t)`, `goldenRoots(t)`, and `goldenClock` (all reused
from `golden_test.go` in the same package). Each Decision is `json.Marshal`-ed and compared
byte-for-byte to the first result via `bytes.Equal`. The test fails immediately on the first
differing index, reporting the divergent bytes.

The helper `builtinPolicies(t)` parses all three built-in policies and returns them in a
deterministic slice order (baseline, slsa-l3, serverless-edge).

### TestEvaluateDeterminism_MultiCVE_VEX

Crafts the multi-CVE VEX DSSE envelope **inline in the test** via `multiCVEVEXEnvelope()`.
The generator approach was not needed; the envelope is constructed programmatically using the
same wire format as `testdata/gen/main.go` (base64-encoded in-toto Statement with OpenVEX
predicate, placeholder empty signature).

The three CVE statements are ordered intentionally as CVE-2024-0003, CVE-2024-0001,
CVE-2024-0002 (non-alphabetical). The `VerifyVEX` function builds a `map[string]string`
from the statements, and `engine.go` line 132 iterates that map with `for cve, status := range`.
Without `sort.Strings(affectedCVEs)` (line 132 engine.go), map iteration would produce a
non-deterministic `AffectedCVEs` slice, causing the policy evaluation reasons to vary.

Evidence uses `goldenEvidence(t)` for the base (image, first 3 attestations, identity) but
substitutes the VEX attestation with the inline multi-CVE envelope. Evaluated against
`builtin.SLSAL3` (which enforces `maxUnmitigatedSeverity: high`, so VEX is in scope).
100 iterations, byte-identical assertion.

## Multi-CVE Envelope: Inline vs Generator

**Approach chosen: inline in the test.**

The envelope is constructed in `multiCVEVEXEnvelope()` using pure Go struct marshaling.
This avoids modifying `testdata/gen/main.go` and keeps the fixture self-contained in the
test file. The generated bytes are deterministic (same struct, same json.MarshalIndent call)
because Go's `encoding/json` marshals struct fields in declaration order (not map iteration
order), and the CVE statements are in a slice (ordered).

## Concerns

None. The determinism sort fix (`sort.Strings(affectedCVEs)`) was already present in
`engine.go` (line 132) before this test was written. The test confirms it works and would
catch any future regression that removes the sort. The `sort.Strings(licenses)` defensive
sort (line 118) is similarly covered by the baseline and slsa-l3 policy tests since SBOM
is in scope for both.

The multi-CVE envelope is constructed inline (not via the generator), which means it is not
persisted as a testdata file. This is the correct approach for a unit-level determinism gate;
the envelope bytes are fully deterministic because they come from JSON-marshaling a Go struct
with a slice (not a map) for the statements.
